\section{High availability and disaster recovery}
\label{sec:hadr}

High availability recovers from minor outages automatically; disaster
recovery restores service after a major one, by hand and from backups
\parencite{schmidt2006ha,llusa2026hadr}.

\subsection{High availability}
\label{sec:hadr-ha}

\begin{itemize}
  \item Three managers keep the Swarm manageable when one node fails
        (\cref{sec:infra-three}).
  \item The stateless services of the app and atenea stacks run two
        replicas. Swarm restarts failed tasks elsewhere, and the routing
        mesh balances requests between replicas.
  \item Health checks let Swarm replace containers that are running but
        no longer working \parencite{llusa2026production}.
  \item Rolling updates replace one replica at a time and roll back
        automatically when the new version fails.
\end{itemize}

\Cref{tab:spof} lists what each failure takes down. It follows from
where the services run; the team did not stop nodes on the cluster to
measure it.

\texttt{swarm-manager-1} is the cluster's single point of failure: it
holds the only public entry, nginx with its certificates, and the NFS
server. Spreading the entry would need the certificates on the shared
disk and an address that reaches several nodes. Replacing the NFS server
would need replicated storage. Both are beyond this project.

\subsection{Disaster recovery}
\label{sec:hadr-dr}

The team placed the services in Schmidt's ``business-important''
category, which allows a recovery time objective (RTO) of three days and
a recovery point objective (RPO) of one day
\parencite{schmidt2006ha,llusa2026hadr}. A company's internal
application and its course platform matter for daily work, but losing
them for hours stops no production line. The next category up,
mission-critical, demands an RTO of eight hours and an RPO of two hours,
which daily dumps on a single cluster cannot give.

Daily backups meet the one-day RPO, and the restore itself is fast:
Moodle's data came back in \qty{21}{\second}. Both objectives hold only
while the backups survive, though. Today they share a disk with the data
(\cref{sec:data}), so losing \texttt{swarm-manager-1} would break the
RPO. Recovery from zero takes four steps, and the second one depends on
the off-site copy that does not exist yet:
\begin{enumerate}
  \item create three machines and the Swarm again, with the NFS export
        (\cref{sec:infrastructure,sec:swarm});
  \item copy the latest backups back to \texttt{/srv/nfs/<stack>/backups};
  \item deploy the basic stack, then the others (\cref{sec:deployment});
  \item restore each stack's latest backup with its restore script, with
        Moodle in maintenance mode.
\end{enumerate}
Only the last step was timed. The full procedure was not rehearsed.
