\section{Infrastructure}
\label{sec:infrastructure}

The cluster runs on three virtual machines in Microsoft Azure, which
Mikael created in his own subscription. \Cref{fig:infra} shows the
layout.

\subsection{Requirements}
\label{sec:infra-requirements}

The statement asks for a Swarm of at least three nodes and leaves the
hosting open: home hardware, virtual machines on a laptop, or a public
cloud \parencite{llusa2026project}. The choice had to meet five
constraints:
\begin{itemize}
  \item three machines that stay on, so the cluster works whenever it is
        checked;
  \item a public address for the front proxy, so Let's Encrypt can
        validate the domain and users can reach the services;
  \item a private network between the nodes for Swarm and NFS traffic;
  \item no cost for the team;
  \item ready within the days left before the deadline.
\end{itemize}

\subsection{Options considered}
\label{sec:infra-options}

\begin{description}
  \item[An existing VPS.] One member rents a VPS, but it hosts unrelated
    production services, and another reverse proxy already owns ports 80
    and 443.
  \item[Team laptops as nodes.] Laptops sleep, change networks and sit
    behind home NAT, so the other nodes often cannot reach them. They
    remain the development environment (\cref{sec:team}).
  \item[One machine running three virtual machines.] The statement
    accepts it, but that one host would be a single point of failure for
    all three nodes.
  \item[Three virtual machines on Azure.] The option chosen. Víctor first
    built a cluster on Azure for Students \parencite{azure-students}. It
    was deleted on 17 October, when Mikael's cluster, already running the
    basic stack, became the team's only cluster.
\end{description}

\subsection{Why three nodes}
\label{sec:infra-three}

Swarm managers keep the cluster state with the Raft consensus algorithm
\parencite{ongaro2014raft,llusa2026orchestration}. A change is committed
only when a majority of managers agree, so a cluster of $N$ managers
survives $\lfloor (N-1)/2 \rfloor$ manager failures
\parencite{docker-raft}. \Cref{tab:raft} shows why two managers are no
better than one, and why three is the smallest cluster that survives a
failure. All three nodes are therefore managers, and they also run
workloads.

\begin{table}[htbp]
  \centering
  \caption{Manager failures a Swarm survives while keeping a majority.}
  \label{tab:raft}
  \begin{tabular}{ccc}
    \toprule
    Managers & Majority & Failures survived \\
    \midrule
    1 & 1 & 0 \\
    2 & 2 & 0 \\
    3 & 2 & 1 \\
    5 & 3 & 2 \\
    \bottomrule
  \end{tabular}
\end{table}

with two AMD vCPUs and \qty{4}{\gibi\byte} of memory, Ubuntu~24.04~LTS
and Docker~29.9, in the Belgium Central region and the resource group
\texttt{rg-ccds-project}. \Cref{tab:vms} shows what makes each one
different. The services that are not pinned to a node run wherever Swarm

\subsection{Network and access}
\label{sec:infra-network}

The machines share one virtual network with a single subnet,
\texttt{10.0.1.0/24}. Network security groups act as the firewall,
outside the machines, and the machines run no firewall of their own.
Azure's default rules allow all traffic inside a virtual network
\parencite{azure-nsg}, so Swarm's ports, 2377/tcp, 7946/tcp+udp and
4789/udp \parencite{llusa2026orchestration}, and NFS on 2049/tcp need no
rule and are never exposed publicly.

At first SSH, HTTP and HTTPS were open on all three machines. The
security review of 17 October flagged it, and on 18 October Mikael
closed them on \texttt{swarm-manager-2} and \texttt{swarm-manager-3}.
Every machine keeps a public address, because new virtual networks have
no default outbound internet access \parencite{azure-default-outbound}.
On 19 October a probe of 17 common ports from outside Azure found only
22, 80 and 443 open, and only on \texttt{swarm-manager-1}. The domain
\texttt{ccds-project.duckdns.org}, a free DuckDNS name, points to that
machine, and its subdomains resolve to the same address.

SSH accepts keys only: password and keyboard-interactive logins are
disabled and root's password is locked. All members log in as the shared
account \texttt{azureuser}, each with their own key, and it has
passwordless \texttt{sudo}. The two private nodes are reached by jumping
through the entry node, with \texttt{ssh -J}. The same review left four
findings open: the shared account, which hides who did what; root logins
with a key, which Azure limits to a message telling users to log in as
\texttt{azureuser}; six authentication attempts per connection; and X11
forwarding.

\subsection{Cost}
\label{sec:infra-cost}

One \texttt{B2als\_v2} machine costs about \$0.04 per hour
\parencite{vantage-b2als}, so the cluster, with its disks and public
addresses, costs about \$4 per day, paid from the credit of Mikael's
subscription.
